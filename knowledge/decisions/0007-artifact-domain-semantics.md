# ADR 0007: Proposed bounded artifact-domain semantics

- **Status:** Proposed; owner and independent review required. No implementation or policy approval implied.
- **Date:** 2026-11-08 (US Central)
- **Tracking:** [Issue #5](https://github.com/kmosoti/CEGAR/issues/5); separate from [Issue #2](https://github.com/kmosoti/CEGAR/issues/2).
- **Design:** [Artifact Domain Semantics v0.1](../../docs/ARTIFACT_DOMAIN_SEMANTICS.md)
- **Baseline inspected:** `3abfcdac81ff65349cea232af10e3aa8f1f0b0cd`; existing finite core and schemas are not an artifact compiler or trusted collection path.

## Context and proposed decision

A checker can prove the graph it receives has no reachable bad state while a faulty compiler omits a real publish attempt, output, failure, or interleaving. A digest can identify bytes without establishing test provenance, freshness, suite applicability or authority. We propose a narrow typed, immutable artifact workflow and a future deterministic Rust/Sans-I/O compiler which preserves every permitted nonviolating prefix and each possible first unsafe attempt, including modeled outcomes and bindings, and maps a complete bounded first-violation monitor graph to the existing core. An unsafe attempt is an explicit edge to a terminal `Bad` monitor with its source and violated rule(s); it has no outgoing edges and does not claim the real operation or scheduler stops. This safety reachability reduction does not represent post-violation effects or establish liveness or goal completion. A failed prerequisite blocks a dependent action only under an explicit success-dependency scheduler contract; blocked status propagates to a deterministic fixed point, while unrelated actions and the declared failure disposition remain modeled. A fully specified true terminal deadlock with no permitted transition can contribute to a scoped safety result but does not establish completion or liveness. An unexplained pending/no-ready stall, omitted scheduler transition or requested unmodeled liveness is inconclusive. Do not delete a dangerous action then verify its remainder. Canonical state representations must retain node/status and producer/output associations rather than sorting bare values into an unsound merge.

The proposal separates authenticated initial observations from claims/predictions and from **hypothetical future test outcomes**. A successful simulated test supports a conditional model path, not a real attestation. Both observed and hypothetical records must satisfy the same scoped policy-validity predicate: pass status, exact subject, suite, runner/collector, issuer trust and integrity, evidence principal versus verification principal, tenant/audience/scope, freshness and revocation, policy/snapshot/tool bindings and all other applicable rules. Evidence principal, runner, issuer and verification/publish principal are separate roles whose identity values may coincide. Permission to run a registered optional suite is distinct from whether its result satisfies publication policy. Hypothetical facts need validated supporting contracts/facts or explicit scope assumptions; a known false predicate is a bad attempted publish or whole-plan rejection, and unknown is never treated as true. Both same-principal use and explicitly policy-permitted cross-principal sharing require compatible tenant, audience, destination and scope; sharing is an owner policy decision, not automatic. A future collector must validate actual provenance; serialization, confidence, a hash or the plan cannot mint authority. Bind an analysis to the exact immutable plan, authenticated principal, snapshot, policy, tool and suite contracts, compiler/verifier, property, graph/mapping, schedule, failures, horizon, budgets and freshness assumptions. A model result has no execution authority and no real-world completeness guarantee. Actual execution, if separately proposed later, requires fresh independent authorization and race-resistant enforcement.

The initial proposed outcomes are exhaustive only in the explicitly stated atomic model: stage success/no-effect failure, test pass/fail/error, and publish success/no-effect failure. Stage success must enumerate all permitted exact output identities and downstream bindings, unless a pinned contract and validated facts guarantee a singleton for the scope; a plan's claimed identity does not establish that guarantee. Unknown/unbounded output possibilities make the broader request inconclusive; an explicitly conditional restriction must identify excluded alternatives. Contract evidence and correctness of any abstraction from real concurrency, partial effects, revocation and failures are not established. Missing semantics or exceeded bounds yield inconclusive for requested coverage; a bounded prefix may be verified only as that explicitly restricted prefix. A safe failure-stopped plan need not achieve its goal. This is a conservative semantic proposal, not an assertion that external systems behave this way.

## Alternatives and tradeoffs

- **Trust serialized `observation` fields or neural confidence:** rejected; attacker or model output could mint evidence and policy permission. A signed envelope alone is also insufficient without a separately trusted validation route.
- **Require only matching digests:** rejected; wrong suite, failed status, forged issuer, stale context or wrong principal can all match the subject. Exact equality remains necessary alongside independently validated conditions.
- **Drop actions with false preconditions:** rejected; this can prove an unsafe submitted plan after silently changing it. Whole-plan rejection is a sound alternative for known invalidity, but the proposed compiler retains ready attempts to yield explanatory modeled witnesses.
- **Always require a pre-existing real test attestation:** easier to reason about but cannot review a future stage/test/publish plan. Hypothetical outcomes permit conditional plan analysis without claiming observation or permission, but must satisfy the same policy-validity requirements. Missing *initial* evidence still stops analysis; a current authenticated fail/error is a known false condition rather than absent evidence.
- **Assume declared stage identity or sort node statuses without their IDs:** smaller representations, but lose feasible output branches or conflate different states; enumerate branch bindings and preserve the keyed state structure. An A/B output branch and P1-to-P2 evidence-sharing case are explicit review fixtures in the design, not executed tests.
- **Assume success-only, one chosen topological order, or unlimited failures:** smaller graph, but hides unsafe branches or overstates scope. Enumerating all permitted atomic schedules and defined branches improves coverage while risking rapid state explosion. Unsupported concurrency and missing branches must be visible, never silently safe.
- **SMT, an execution engine, external workflow service or general plugin framework now:** not necessary for this small graph design and expands the trusted/dependency surface. Later symbolic representations need equivalent coverage and independent validation, not a weaker property.

## Compatibility and migration

At this baseline [`Model::new`](../../crates/cegar-core/src/lib.rs) accepts dense indices and `u32` action labels, a nonempty initial set and at most 128 states/512 edges. The core outcome scope is always `supplied_finite_model_only` and authorization always false. It neither validates source policy nor implements domain semantics. A future wrapper must establish and bind its own graph construction, mapping, coverage, evidence and receipt; it cannot upgrade an arbitrary supplied graph to trusted status. Limit failures reject the complete compilation as inconclusive, not partial success. The present ADR does not change the core or its public API.

The draft [plan schema](../../schemas/plan.proposed.schema.json) and [example](../../examples/stage-test-publish.proposed.json) have string refs and a digest-shaped attestation but lack the authenticated principal, versioned operation and suite identities, provenance, scheduler, failure choices and full bindings required by this proposal. Their parse validity is not semantic or trust validation; no existing example is evidence of a real test. The [finite-model schema](../../schemas/finite-model.proposed.schema.json) uses explicit numeric states, bit width and string action labels, unlike dense core IDs and numeric labels. An adapter must validate and deterministically map them; schema shape does not enforce graph/domain completeness. The draft [result schema](../../schemas/verification-result.proposed.schema.json) lacks mandatory complete lineage, model mapping, failure/schedule coverage and validity details. Its `trusted_snapshot_and_policy` label must not be emitted just because a client supplies refs. New fields/variants, canonicalization and migrations require a separate schema/contract decision, negative fixtures and clients that safely reject unknown variants. No schema is changed by this ADR.

## Unresolved decisions and evidence

Owner decisions include approved hash/canonicalization and namespacing, authentication and revocation, time source/freshness and cross-snapshot compatibility, policy/suite composition and cross-principal/tenant/audience evidence sharing, supported stage-output contracts, allowed scheduler/atomicity and failure contracts, bounded-prefix result presentation, and the trust boundary for collecting actual test outcomes. Additional supported tools, execution or a network API require separate scope/security review. [ADR 0002](0002-bounded-sans-io-core.md) provides the Rust-native boundary; [ADR 0003](0003-finite-cegar-kernel.md) and [ADR 0005](0005-raw-fixture-reference.md) describe limitations of the current core and its reference tests. Those tests do not validate this proposal.

A missing reachable unsafe attempt, unmodeled failure/interleaving reported as fully safe, unauthorized trusted observation, mismatched attestation accepted, silent size truncation, irreproducible encoding, or non-replayable witness falsifies the corresponding safety claim. Future acceptance requires independent domain-oracle differential testing on small raw synthetic plans, negative/mutation and resource tests, review of the compiler/collector trust boundary, exact revision-specific CI and an explicit owner decision. No such tests, measurements or qualification are claimed by this design record.

## Reversal and recovery

Revisit or replace this proposal if reviewed contracts cannot faithfully serialize real schedules/failures, the finite caps prevent useful scope, reliable provenance cannot be established, or differential/adversarial evidence finds unsound compilation. A replacement must retain fail-closed outcomes, identity/provenance and no-execution guarantees; changing the model or schema requires an explicit compatibility and security review. This documentation-only proposal can be reverted without changing runtime behavior; no graph, collector, endpoint, executor or dependency is introduced.
